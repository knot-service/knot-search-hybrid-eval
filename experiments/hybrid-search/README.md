# Workspace 검색 비교

기존 Knot 탐색 평가실의 **하이브리드 검색 실험** 메뉴에서 검색 방식 비교, 문서 찾기, 회의 종합을 실행한다. 이 폴더의 Python 실행기는 로컬 포트 18173으로 연결된다. 기준 브랜치는 Knot `be/refactor/#715`의 `cb08773ab`다.

## 로컬 실행

이 폴더에서 Python 3.12와 Docker를 사용한다.

```sh
uv venv --python 3.12
uv pip install -r requirements.txt
.venv/bin/python database.py prepare
docker compose --project-name knot-hybrid-search up -d --wait
.venv/bin/python snapshot.py /path/to/knot-search-lab/experiments/workspace458-v130-separate-fixture-crosswalk-20261111.json
.venv/bin/python database.py .local/workspace458.json
KNOT_EVAL_ENV_FILE=/path/to/knot/backend/.env.search-local ./launch-local.sh
```

458은 기존 Playground DB에서 현재 합성 멤버 1의 DRAFT·ARCHIVED 문서를 조회한다. Eval DB의 잠긴 v1.30에서 질문과 기대 근거만 읽고, 별도 실행 조건이나 대화 이력이 필요한 사례와 기대 근거가 없는 사례를 제외한다. 두 소스는 읽기 전용으로 조회한다. 생성 요청에는 기존 Eval의 `LLM_*` 설정을 사용한다.

별도 PostgreSQL은 로컬 55448에서 실행되고 `workspaces.id`로 코퍼스를 구분한다. 운영 Workspace 1을 가져올 때는 권한이 확인된 연결에서 `psql -XqAt -v ON_ERROR_STOP=1`로 `workspace1.sql`을 실행하고, 출력은 권한 600의 `.local/workspace1.json`으로 받는다. `.venv/bin/python database.py .local/workspace1.json`으로 로컬 DB에 가져온 뒤 작업용 덤프 파일을 삭제할 수 있다. 운영 덤프에는 검색용 문서와 녹음 시작 시각만 들어간다. 현재 실행기는 합성 458에만 질의하고 Qwen에도 458 근거만 보낸다.

## 비교 조건

- 기준 시각은 2026-11-11 00:00 KST다. 90개 합성 문서와 기대 근거가 있는 단일 턴 55개 질문을 사용한다.
- 세 방식은 제목·주제·요약을 공통 검색 표현으로 쓴다. 요약이 비면 본문 앞 750자를 사용한다. 키워드는 BM25, 벡터는 CPU에서 multilingual-e5-small로 임베딩한 뒤 pgvector에서 정확 코사인 검색, 하이브리드는 각 방식의 상위 20개를 RRF로 결합한다.
- 측정은 문서 단위 Recall@10, 모든 기대 근거 포함률, 검색 p50·p95다. 검색 시간은 벡터 모드의 질문 임베딩을 포함한다. 하이브리드 시간은 두 검색과 결합의 합이다. 프로세스 시작과 문서 임베딩은 검색 시간에서 제외한다.
- 문서 찾기는 녹음 시각과 배포·안정성 주제로 가장 최근 회의를 찾은 뒤 하이브리드 후보를 반환한다. 종합은 같은 기준의 최근 세 회의에서 한 건씩 근거를 뽑아, 본문의 관련 단락과 요약을 Qwen에 제공한다.
- 실행 결과는 `.local/runs/`에 기록한다. 첫 모델 응답 시간은 실행 시작부터 첫 내용 토큰까지다. 화면에는 전체 응답 수신 후 답변과 출처를 표시한다.

## 4차 Spring Boot 검색 경로

Spring 탐색 Worker에 실험 경로를 추가했다. 기존 질문 API와 SSE 형식으로 세 경로를 실행한다. Spring이 현재 멤버십·실행 권한을 확인하고, 검색 시작 시각까지 생성된 DRAFT·ARCHIVED 문서를 워크스페이스와 녹음 날짜로 제한한다. 로컬 검색 서비스는 허용된 문서 ID에서 고정 길이 Child를 대상으로 BM25와 E5/pgvector의 상위 20개를 RRF로 결합한다. Spring은 반환 ID를 다시 확인하고 자체 DB에서 제목·본문을 읽는다.

- 문서 찾기는 기존 SSE와 문서 링크 규격으로 최대 3개를 전달한다. 의도 분류 모델과 답변 생성기 호출은 0회다.
- 회의 내용 질문은 관련도순 후보를 기존 Qwen 생성기에 전달한다.
- 여러 회의 종합은 회의별로 후보를 확보하고 녹음 시각순으로 Qwen에 전달한다. 질문에서 인식한 최근 회의 개수가 있으면 후보 회의에 적용한다. 스트리밍 요청에 답변 JSON 스키마를 지정하며 기존 파서가 응답과 인용 ID를 확인한다.

## 5차 Spring Worker 리랭킹·Parent 문맥과 주장별 출처

1. Spring의 권한·날짜 필터를 거친 문서로 Child 검색과 RRF를 실행한다. 문서 찾기는 결과 링크를 반환하며 Cross-Encoder, 문맥 조립, 생성 모델 호출을 모두 건너뛴다.
2. 내용 질문과 여러 회의 종합은 RRF 상위 20개 청크를 3차에서 쓴 multilingual MiniLM Cross-Encoder로 재정렬한다. 내용 질문은 한 문서에 청크가 몰리지 않도록 대표 문서를 먼저 선택하고, 여러 회의 종합은 회의마다 대표 청크를 하나씩 선택한다. 문맥은 최대 5개 구절에 E5 토크나이저 기준 1,024토큰을 배분하고 주변 Parent 단락으로 확장한다. Spring은 종합 문맥을 DB의 녹음 시각순으로 정렬한다.
3. Spring은 각 후보의 ID, 본문·요약 종류, 유니코드 문자 범위와 구절을 현재 DB 원문에 다시 맞춰 본다. 확인한 구절만 Qwen에 보낸다. 응답은 주장과 인용 구절을 담는 JSON이다. 서버는 출처가 각 주장에 실제로 붙어 있고 인용 구절이 제공한 단일 구절 안에 있는지 확인한 뒤 사용자에게 보낸다. 기존 원문 링크 규격은 서로 다른 문서 최대 3개를 저장한다. 인용의 의미가 주장 전체를 지지하는지는 실측 답변을 별도로 판정한다.

### 6차 후속: 내용 질문 지연 구간 재실측

동일 커밋에서 문서 찾기 슬롯만 0과 1로 바꿔 각각 예열 6건과 동시 3·6건 12회씩을 실행했다. 두 실행에서 같은 동시성·회차·워크스페이스·사례를 대조한다. 평가 로그는 응답 ID로 Worker 접수 대기, 검색 전체, 검색에 포함된 리랭킹, Qwen 스트림을 결합한다. Qwen 첫 내용 대기는 Spring의 HTTP 요청 시작부터 첫 모델 내용까지로, 네트워크·모델 서버 대기·입력 처리 시간이 포함된다. 이후 생성은 첫 내용부터 Qwen 스트림 종료까지다. 서버 내부 큐를 개별 요청으로 분리할 지표는 이 엔드포인트에서 제공받지 못했다.

Spring은 구조화된 모델 응답 전체를 받은 뒤 출처를 검증하고 첫 사용자 답변을 SSE로 전송한다. 첫 SSE에는 첫 내용 대기와 이후 생성이 모두 들어간다. 구간별 p95는 서로 다른 요청에서 나올 수 있으므로 각 값을 더하지 않는다. Lab에는 첫 SSE p95·p99에 해당하는 실제 요청의 구간도 따로 표시한다.

동시 6건에서 이전 6차의 내용 질문 지연 증가(7.405 → 9.125초)는 재현되지 않았다. 이번 첫 SSE p95 요청의 가장 긴 구간은 Worker 대기였으며 공용 5.199초, 분리 5.701초였다. 이 두 요청의 Qwen 스트림 전체는 2.767 → 1.977초였다. Worker 대기만 별도로 집계한 p95는 5.199 → 4.949초였다. 반복마다 각 경로의 대기와 생성 시간이 달라지므로 한 번의 전후 차이로 Worker 분리의 인과 효과를 단정할 수 없다.

두 설정에서 각각 108건이 완료됐고 문서 찾기 36건씩의 생성·분류 모델 호출은 모두 0회였다. 문서 찾기 첫 SSE p95는 동시 3건에서 3.035 → 0.260초, 동시 6건에서 6.503 → 0.364초였다. 생성 요청 72쌍에서 기대 회의가 검색 문맥에서 줄어든 사례는 0건이었다. 표시 인용의 원문·저장 출처 일치는 198/198 → 174/174개였고, 근거 부족 안내로 끝난 답변은 7/72 → 9/72건이었다. 같은 동시 6건 질문 10개의 첫 완료 답변에서 주장 전체를 지지한 인용은 18/20 → 11/13개였다. 분리 후 두 답변은 주장을 표시하지 않아 의미 검수 분모에서 빠졌다. 기대 회의를 모두 인용한 종합은 Workspace 1에서 2/3 → 2/3건, Workspace 458에서 3/3 → 2/3건이었다. 이 표본에는 기대 문서가 문맥에 남아 있었지만 최종 인용이 비어 있던 답변이 포함됐다.

### 6차 후속: 내용 질문과 회의 종합의 생성 Worker 분리

`SEARCH_SPLIT_GENERATION_ROUTES=true`는 생성 슬롯 중 하나를 종합에 배정하고 나머지를 내용 질문에 배정한다. 이 실험은 생성 슬롯 합계 2개와 문서 찾기 슬롯 1개로 두 설정을 비교했다. 옵션 기본값은 `false`다. 분리 설정은 생성 슬롯 2개 이상과 문서 찾기 슬롯 1개 이상이 필요하다. 한쪽 슬롯이 비어 있어도 다른 경로에 빌려주지 않으므로, 요청이 한 경로에 몰릴 때는 해당 경로의 대기가 늘 수 있다.

접수 및 재시도 시 기존 하이브리드 질문 분류 규칙으로 내용 질문의 대기열을 저장한다. 기존 대기 행과 하이브리드 대상 밖의 작업은 종합과 같은 슬롯에서 처리한다. 실행을 시작할 때 저장된 대기열을 잠금 안에서 다시 확인하므로, 스케줄러가 조회한 뒤 재시도로 대기열이 바뀐 작업은 이전 슬롯이 가져가지 않는다. 리랭킹, 문맥 조립, 모델과 출처 검증은 같은 설정을 쓴다.

S18-01은 양쪽 모두 6/6건에서 기대 문서를 문맥에 넣었고, 최종 인용은 1/6 → 6/6건, 인용이 전혀 없던 답변은 5/6 → 0/6건이었다. 표시 인용은 50/50 → 62/62개가 원문과 저장 출처에 일치했다. 초기 분리 재실행에서는 S18-01이 6/6건 인용했지만 S71-01에서 누락이 있었다. 두 설정에서 모델·프롬프트와 인용 검증이 동일하므로 최종 인용 차이를 슬롯 분리의 효과로 단정할 수 없다.

### 6차 후속: 내용 질문 우선 슬롯 공유

`SEARCH_SPLIT_GENERATION_ROUTES=true`에 `SEARCH_SHARE_GENERATION_SLOTS=true`를 더하면 두 생성 슬롯을 한 실행기에서 사용한다. 작업을 꺼낼 때 대기 중인 내용 질문을 먼저 선택하고 같은 경로 안에서는 접수 순서를 따른다. 남은 슬롯은 종합 작업을 처리한다. 한 경로만 대기하면 그 경로가 두 슬롯을 모두 쓸 수 있다. 이미 시작한 요청은 끝까지 실행하며, 지속적으로 내용 질문이 밀리면 종합의 대기가 길어질 수 있다. 문서 찾기 슬롯과 모델·프롬프트는 동일하다.

공용과 고정 분리는 직전 실험의 실측값을 재사용한다. 슬롯 공유는 같은 두 워크스페이스의 같은 질문을 동시 3·6건 각각 12회 재실행한다. 비교 스크립트는 세 실행의 입력 스냅샷, 회차별 사례, 슬롯 수와 SSE 측정 설정을 검증한다. Worker 로그에서 한 경로의 두 작업이 서로 다른 생성 슬롯에서 겹친 횟수도 집계한다. 별도 실행의 모델 응답과 부하가 변동할 수 있다.

이전 실험과 같은 환경에서 저장소 루트에서 실행한다.

