# 하이브리드 검색 정확도 전체 개선 계획

목표는 날짜 해석부터 최종 발췌까지 다섯 단계에서 기대 근거가 빠지는 이유를 줄여, 답변 모델에 전달되는 근거와 실제 답변의 인용 품질을 높이는 것이다. 각 단계의 효과를 같은 질문으로 비교한 뒤 채택한 변경을 함께 검증한다.

## 기준선

Workspace 1에서 기대 원문 구절 526개 중 295개(56.1%)가 최종 문맥에 들어갔다. 중간 단계는 후보의 원문 또는 현재 Parent 확장 범위로 기대 구절 전체를 담을 수 있는지, 최종 단계는 실제 전달 구절이 이를 담았는지로 센다. 한 구절의 최초 누락은 한 단계에만 기록한다.

| 단계 | 통과 구절 | 이 단계에서 처음 빠진 구절 |
| --- | ---: | ---: |
| 날짜 필터 | 515 | 11 |
| 키워드 또는 벡터 검색 후보 | 501 | 14 |
| RRF 통합 후보 | 476 | 25 |
| 리랭킹 후 문맥 선택 | 326 | 150 |
| 최종 발췌 | 295 | 31 |

기존 비교값은 Workspace 1의 기대 회의 전체 포함 131/140건과 Workspace 458의 6/8건이다. Workspace 458의 기대 구절 표본은 7/7개로, 회귀 확인에 사용한다. 답변 품질 기준선과 고정 평가 자료는 [정확도 1차 기록](README.md#정확도-1차-리랭킹과-parent-문맥)을 따른다.

## 준비 — 같은 실행에서 단계별 근거를 비교할 수 있게 만들기

- [Spring 재생 테스트](../../backend/src/test/java/com/knot/backend/search/application/SearchHybridDatasetReplayTest.java)에 검색 전용 재생을 마련한다. 실제 Spring 권한·날짜 필터를 거쳐 Python 검색 서비스를 호출한다. 반복 실험은 Qwen 없이 돌리고, 답변 비교는 통합 후보가 정해진 뒤 수행한다.
- 동일한 문서 스냅샷, 질문과 기대 구절, 모델 버전, 기준 시각과 시간대를 고정한다. 질문마다 허용 문서, 검색기별 후보, RRF 전후 순위, 선택된 청크, Parent 범위, 최종 원문 위치를 수집한다. 기존 기준선 295/526개를 재현하고, 차이가 생기면 사례와 실행 조건을 확인한 뒤 비교 기준을 확정한다.
- 구절은 사례 ID, 문서 ID, 본문 또는 요약, 원문 시작·끝 위치로 대조한다. 기존에 포함된 구절 중 빠진 수와 새로 포함된 수를 둘 다 기록한다. 상한에 걸리거나 다른 청크가 선택된 경우에는 해당 이유도 남긴다.
- 알려진 실패 사례로 후보를 비교하고, 가능하면 튜닝에 쓰지 않은 회의와 질문 묶음을 별도로 평가한다. 같은 회의의 표현 변형은 한 묶음으로 취급한다. 새 평가셋이 아직 없다면 결과 범위를 고정 평가셋으로 명시한다.

## 실행 순서

### 1. 리랭킹 후 문맥 선택

누락 150개 중 123개는 같은 회의의 다른 문서에 밀렸고, 그중 81개는 5개 슬롯을 다 쓰지 않은 요청에서 빠졌다. 22개는 같은 문서의 다른 청크가 선택됐고, 5개는 해당 문서나 회의가 선택 범위 밖이었다.

1. 회의 종합에서 기존 규칙대로 회의별 대표 하나를 고른 뒤, 남는 슬롯을 해당 회의의 두 번째 관련 문서에 리랭킹 점수순으로 배정한다. 최근 N개 회의 요청에서 선택한 회의 집합을 지키고, 회의당 추가 문서는 우선 하나로 제한한다. 전체 5개 구절과 1,024토큰 안에서 비교한다.
2. 별도 변형에서 같은 문서의 두 번째 청크도 허용한다. 문서가 같아도 원문 위치가 겹치지 않는 구절을 대상으로 한다. 두 방식이 같은 빈 슬롯을 두고 경쟁하면 기존 순위, 회의별 보충, 두 방식의 조합을 각각 비교한다.
3. 모든 슬롯이 찼거나 기대 회의가 선택 범위 밖인 사례는 따로 본다. 필요하면 회의 후보 순서를 먼저 비교하고, 기대 회의가 여럿인 질문의 대표 슬롯을 보조 구절이 밀어내지 않도록 한다.

수정 후보는 [회의별·문서별 선택 로직](phase4_retrieval.py)이다. 첫 재현은 RRF 1위에서 리랭킹 2위로 내려간 뒤 같은 회의의 1위 문서에 밀린 `W1-0327-01`로 한다. 회의별 포괄성, 회복·신규 누락 구절 수, 실제 전달 토큰 수로 변형을 비교한다. 빈 슬롯을 채워도 공유 토큰 예산 때문에 기존 구절이 잘릴 수 있으므로 최종 발췌까지 검사한다.

### 2. 날짜 필터

1. `10월 22일이랑 23일`처럼 뒤 날짜에서 월이 생략된 표현을 읽는다. 날짜를 나열하면 해당 날짜들의 합집합을 쓰고, `부터 …까지`로 기간을 표현하면 연속 범위를 쓴다. 떨어진 날짜의 합집합을 위해 [날짜 파서](../../backend/src/main/java/com/knot/backend/search/application/SearchHybridQuestion.java)에서 [DB 검색 범위](../../backend/src/main/java/com/knot/backend/search/infrastructure/persistence/SearchHybridDocumentScope.java)로 여러 구간을 전달하는 방식을 검증한다.
2. `6월이 … 맡긴 업무`처럼 주체로 쓰인 표현이 월 필터를 만들지 않도록 한다. `6월 회의`, `6월에`, `6월이 지나기 전에` 같은 실제 시간 표현과 쌍으로 확인한다. 한국 시간 자정 경계와 기존 상대 날짜 사례도 재생한다.
3. 기존 누락 11개의 기대 문서가 날짜 필터를 통과하는지 확인하고 최종 구절까지 추적한다. 날짜 사이에 끼어 있는 회의, 다른 워크스페이스 문서, 권한 밖 문서는 실제 Spring 경로에서 제외되는지 검증한다.

### 3. RRF 통합

1. 검색기별 입력 20개와 현재 RRF 점수식을 고정한다. 리랭커에 넘기는 수만 20개, 30개, 중복을 제거한 합집합 전체로 비교한다. 현재 검색 입력과 RRF 출력이 같은 상수를 쓰므로 [RRF](phase2.py)와 [호출부](phase4_retrieval.py)에서 두 한도를 독립적으로 제어한다.
2. 이미 찾았으나 RRF에서 빠진 25개의 회복과 리랭킹 p95를 비교한다. 한 검색기에서만 찾은 후보가 계속 밀리면 각 검색기 상위 후보를 소수 보장하는 변형을 별도로 시험한다. 입력 깊이와 점수식을 같은 실험에서 함께 바꾸지 않는다.
3. 문서 찾기는 리랭커를 거치지 않으므로 리랭커 입력을 늘리는 실험과 문서 결과 목록의 변화는 별개로 비교한다.

### 4. 키워드·벡터 검색

1. 현재 청킹·임베딩으로 키워드만 20→30→40, 벡터만 20→30→40을 각각 비교한다. 앞 단계에서 선택한 RRF 출력 한도를 적용하고, 조합 실험은 각 검색기의 효과를 확인한 뒤 진행한다.
2. 원래 빠진 14개가 어느 검색기에서 어느 순위로 돌아오는지 보고, 회복되지 않은 사례는 관련 문서 부재, 문서 안의 다른 청크 선택, 키워드 표현 차이로 나눠 확인한다. 토큰 분리 문제라면 키워드 정규화를, 청크 경계 문제라면 기존 Markdown 구간 청킹과 고정 길이 청킹을 별도 실험으로 비교한다.
3. 인덱스 변형은 기존과 후보가 같은 원문 스냅샷을 사용하도록 각각 검증한다. 후보 단계의 구절 증가가 최종 문맥으로 이어지고 검색 지연에 합리적인 비용인지 판단한다.

### 5. 최종 발췌

1. [문맥 조립](phase3.py)에서 선택된 청크, Parent 범위, 전체 1,024토큰을 고정해 기존 발췌와 질문에 가장 관련 있는 문장 중심 발췌를 비교한다. 의미가 끊기지 않는 원문 구간을 선택하고, 문장 경계와 원문 문자 위치를 확인한다.
2. 동일 후보와 발췌 규칙에서 약한 청크의 96토큰 제한을 완화한 실험을 따로 돌린다. 관련 구절에 예산이 돌아가는지와 무관한 문맥이 늘어나는지를 같이 본다.
3. 발췌 규칙을 고른 뒤 전체 예산을 1,024·1,536·2,048토큰으로 비교한다. 31개 중 완전한 구절이 얼마나 회복되는지, 기존 회의별 근거가 어느 정도 유지되는지, 실제 전달 토큰이 얼마나 늘어나는지 확인한다. 예산이 달라진 뒤 RRF와 두 검색기 조합을 한 번 더 비교한다. 총 토큰과 구절 개수는 [Spring 검증](../../backend/src/main/java/com/knot/backend/search/application/SearchHybridWorkflow.java)에서도 검사한다.

## 채택과 완료 기준

- 각 단계에서 직전 채택본과 한 가지 변형을 비교한다. 최초 누락 건수, 새로 포함된 구절, 새로 빠진 구절, 최종 포함률과 기대 회의 전체 포함률을 함께 기록한다. 알려진 실패가 다음 단계로 옮겨갔더라도 실제 최종 문맥에 들어오기 전까지는 회복으로 계산하지 않는다.
- 단계별 후보는 목표로 삼은 누락을 줄여야 한다. 통합 후보의 기본 채택 기준은 Workspace 1 최종 295/526개 초과, 기대 회의 전체 포함 Workspace 1의 131/140건과 Workspace 458의 6/8건 이상, Workspace 458의 기대 구절 7/7개다. 총합이 통과하더라도 새로 누락된 사례를 검토한다. 회복과 손실이 상쇄되거나 성능 비용이 커지면 상한이나 선택 규칙을 조정해 다시 비교한다.
- 동일한 실행 조건으로 검색·리랭킹·문맥 조립의 p95와 토큰 수를 비교한다. 통합 후보는 실제 Qwen·SSE에서도 두 워크스페이스의 원문 인용 일치, 주장별 근거 충실도, 기대 회의 인용을 검증한다. `S18-01`은 모델 입력, 모델 인용, 최종 검증을 대조한다. 문서 찾기의 생성·분류 모델 호출은 각각 0회인지 확인한다.
- 최종 비교는 원본 기준선과 통합 후보를 같은 조건으로 재실행한다. 다섯 단계별 채택 결과, 남은 누락, 최종 비교 수치, 재현 절차를 정리하고 Lab·Notion에는 집계 결과를 반영한다. 사례별 원문과 모델 입력을 담은 보고서는 로컬 실험 자료로 관리한다.

두 번째 문서만 넣었을 때 18문항에서 27구절이 돌아왔고, 11문항에서 기존 구절 20개가 빠졌다. 신규 누락 20개 중 14개는 문서 #579였다. `selection.json`은 해당 변형의 `gained`와 `lost`에 사례 ID, 문서 ID, 본문·요약 구분과 원문 위치를 기록한다.

날짜 실험에서 기대 문서가 검색 범위를 통과한 구절은 515개에서 526개로 늘었다. RRF는 출력을 30개로 늘리면 리랭커에 도달한 기대 구절이 493개에서 515개로 늘었지만, 회의별 문맥 선택에서 빠진 구절이 증가했다. 2,048토큰으로 재검증했을 때도 RRF 22·25·30개는 각각 366·357·358개, 합집합은 340개였다. 검색기별 후보 4·8개를 예약한 변형은 374·373개였고, 키워드 40개에 벡터 30·40개를 조합한 변형은 371·362개였다. 통합 설정은 키워드 40개, 벡터 20개, RRF 20개를 사용한다.

1,536토큰과 2,048토큰의 최종 포함 차이는 3구절이다. Workspace 1의 실제 전달 토큰 p95는 1,536에서 약 1,713으로 증가했다. 2,048은 상한이며, 문맥이 짧은 요청은 필요한 만큼만 사용한다.
